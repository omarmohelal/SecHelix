# AI-Built App Launch Audit

A practical launch-focused SecHelix profile for AI-generated, agent-generated, rapidly prototyped, and "vibe-coded" applications.

Use this profile when the question is not "did we run a scanner?" but "can we prove the minimum security guardrails exist before launch?"

## Core rule

A control does not count as present merely because it is expected, documented, generated by a framework, or visible in the UI.

**Do not mark a launch check PASS unless you can point to concrete evidence** such as code, configuration, policy, a test, a deployed response, or a relevant log proving the guardrail actually exists on the path being assessed.

If evidence is missing or ambiguous, report `UNKNOWN`. If the check is relevant and the guardrail is absent or bypassable, report `FAIL`. If architecture evidence proves the capability does not exist, use `NOT_APPLICABLE`. If scope, authorization, access, or environment prevents a legitimate decision, use `BLOCKED`.

## Workflow

1. **AUDIT** — map the application and evaluate the launch checks that apply.
2. **FIX** — repair `FAIL` items and resolve `UNKNOWN` items that matter to launch.
3. **VERIFY** — test the real trusted boundary, preferably the deployed path in an authorized environment.
4. **RE-RUN** — repeat after major auth, payment, data-model, infrastructure, deployment, or agent/tooling changes.

Never mutate production data or infrastructure merely to prove a checklist item. Use `STATIC`, `LOCAL`, authorized `STAGING`, or bounded `PRODUCTION_SAFE` evidence according to the normal SecHelix rules.

## Result contract

For every applicable launch check return:

- **Result** — `PASS`, `FAIL`, `UNKNOWN`, `NOT_APPLICABLE`, or `BLOCKED`.
- **Evidence** — exact file/config/policy/test/log/runtime observation supporting the result.
- **Failure mode** — for `FAIL` or security-relevant `UNKNOWN`, one concise realistic consequence.
- **Smallest safe fix** — the minimum root-cause correction, not cosmetic UI hardening.
- **Verification** — the specific safe assertion or test that proves the fix/control on the trusted boundary.

Prioritize launch blockers involving authentication, authorization, tenant or user isolation, private data, payments or entitlements, admin authority, secrets, AI/tool authority, externally triggered actions, or uncontrolled spend.

## Launch checks

The checks below are a practical view over SecHelix's existing security families. They do not replace the full hypothesis catalog; they provide a compact launch gate for common failures in AI-built applications.

### Secrets, authentication, data access, and input

| # | Launch check | SecHelix families | What PASS must prove |
|---:|---|---|---|
| 01 | Database credentials are not exposed | `CRYPTO`, `CLOUD`, `CI` | Connection credentials remain on trusted server/platform boundaries and any previously exposed credential has been replaced. |
| 02 | Environment files are not publicly reachable or shipped | `CRYPTO`, `REL`, `CI` | Env files are excluded from source/public artifacts and production secrets come from trusted secret storage. |
| 03 | Private API keys and secrets are not hardcoded | `CRYPTO`, `SUPPLY`, `CI` | Private credentials are obtained from trusted server-side secret storage and committed leaks are treated as compromised. |
| 04 | Private functionality requires real authentication | `AUTH` | Every private route/action resolves an authenticated subject on the trusted server boundary. |
| 05 | Sensitive actions enforce server-side authorization | `AUTHZ` | The server checks role/ownership/tenant/object authority before the privileged action or data access occurs. |
| 06 | Users and tenants cannot cross each other's data boundary | `AUTHZ`, `DB` | Two-identity tests or equivalent policy evidence show reads and writes are scoped to the authenticated owner/tenant. |
| 07 | Database permissions follow least privilege | `DB`, `CLOUD` | RLS/ACL/grants/service roles deny unintended reads or writes by default and grant only required capabilities. |
| 08 | Managed database/storage rules are correctly restricted | `DB`, `CLOUD`, `FILE` | Firebase/Supabase/object-storage policies are tested signed out and as the wrong user/tenant, not merely inspected in the dashboard. |
| 09 | Admin routes/actions are server-guarded | `AUTHZ`, `OPS` | Admin authority is enforced server-side for direct requests; hidden navigation or an obscure URL is not the control. |
| 10 | Production does not expose debug or developer tooling | `OPS`, `REL`, `CLOUD` | Debug consoles, profilers, test endpoints, internal dashboards, and development helpers are absent or strongly access-controlled in production. |
| 11 | Build and CI output does not disclose secrets | `CI`, `PRIV`, `CRYPTO` | Logs and scripts mask credentials and do not print tokens, keys, connection strings, or other reusable secrets. |
| 12 | Production errors do not disclose internals | `API`, `PRIV`, `OPS` | User-facing errors are bounded while stack traces, queries, filesystem paths, and internal details remain in restricted diagnostics. |
| 13 | Git history does not contain usable live secrets | `CRYPTO`, `SUPPLY`, `CI` | Any secret ever committed is rotated/revoked; deletion from the current tree alone is not considered remediation. |
| 14 | Browser bundles contain no private service credentials | `CRYPTO`, `WEB`, `REL` | Production JavaScript/assets expose only values safe for any end user to read. |
| 15 | Security decisions are not enforced only in client code | `AUTHZ`, `WEB`, `BIZ` | Validation, authorization, entitlement, price, role, and ownership decisions are repeated at the trusted server boundary. |
| 16 | Untrusted input is validated server-side | `INJ`, `API`, `FILE` | Type, shape, length, size, format, enum/range, and unexpected-field handling are enforced before sensitive sinks. |
| 17 | SQL query construction resists injection | `INJ`, `DB` | User input reaches SQL only through parameter binding/safe query APIs, with no reachable concatenated interpreter path. |
| 18 | NoSQL/object query construction resists injection | `INJ`, `DB`, `API` | User-controlled objects/operators cannot alter query semantics outside an explicitly allowed shape. |

### Web, sessions, APIs, files, and payments

| # | Launch check | SecHelix families | What PASS must prove |
|---:|---|---|---|
| 19 | Untrusted content cannot become executable browser code | `WEB`, `INJ` | Output encoding/sanitization and framework behavior prevent attacker-controlled script execution on reachable paths; CSP is used where appropriate. |
| 20 | Browser-authenticated state changes resist CSRF | `WEB`, `SESS` | Cookie policy and framework/application CSRF defenses protect relevant state-changing requests. |
| 21 | File uploads are constrained and safely handled | `FILE` | Size/type/content rules, safe naming/storage, parser boundaries, and serving behavior prevent dangerous or unintended file execution/access. |
| 22 | User-controlled paths cannot escape approved storage roots | `FILE` | Canonicalization/resolution keeps file access inside an intended base and rejects traversal/absolute-path variants. |
| 23 | Server-side URL fetching cannot reach forbidden destinations | `SSRF` | Destination policy, scheme handling, DNS/redirect behavior, and private/internal range controls prevent unauthorized internal access. |
| 24 | Password recovery cannot be replayed or abused | `AUTH` | Reset tokens are strong, short-lived, single-use, invalidated correctly, and the flow does not unnecessarily disclose account existence. |
| 25 | Session lifecycle is securely managed | `SESS`, `AUTH` | Tokens/cookies have appropriate entropy, expiry, rotation, revocation, logout invalidation, and reauthentication behavior. |
| 26 | JWTs are validated as security tokens, not merely decoded | `SESS`, `CRYPTO`, `AUTH` | Signature, allowed algorithm, issuer, audience, expiry, and other required claims are verified against trusted configuration. |
| 27 | CORS grants only the cross-origin access actually required | `WEB`, `API`, `CLOUD` | Allowed origins/methods/headers/credentials are explicit and tested for both approved and attacker-controlled origins. |
| 28 | Abuse-sensitive endpoints have effective rate limits or equivalent controls | `API`, `AUTH`, `AI`, `OPS` | Login/signup/reset/API/AI/spend-sensitive paths enforce bounded per-identity and/or per-origin abuse controls at the trusted boundary. |
| 29 | Staging/test systems are not public backdoors into production trust | `CLOUD`, `OPS`, `REL` | Non-production systems are authenticated as needed and do not carry unnecessary production secrets, customer data, or privileged admin tooling. |
| 30 | Vendor/default credentials and accounts are removed or changed | `AUTH`, `OPS`, `CLOUD` | Known defaults cannot authenticate and unused bootstrap/default identities or tokens are disabled. |
| 31 | Webhook events are authenticated before side effects | `API`, `CRYPTO`, `RACE` | Provider signatures/MACs and replay/idempotency requirements are verified before trusting event contents or mutating state. |
| 32 | Payment and entitlement truth is decided server-side | `MONEY`, `BIZ`, `AUTHZ` | Subscription, price, paid state, quantity, ownership, and entitlement are derived from trusted server/provider state rather than browser claims. |
| 33 | Object-level authorization prevents IDOR/BOLA | `AUTHZ` | Possessing or guessing an object ID is insufficient; the server authorizes the specific action against the specific subject/object relationship. |
| 34 | APIs do not trust client-supplied roles, owners, or subject IDs as authority | `AUTHZ`, `API` | Identity and privilege come from trusted auth context; request fields cannot self-assign role/tenant/owner/user authority. |
| 35 | Logs do not retain unnecessary sensitive data | `PRIV`, `CRYPTO`, `OPS` | Passwords, tokens, payment secrets, and unnecessary PII are redacted/minimized, with restricted access and appropriate retention. |
| 36 | Production source maps and build artifacts do not leak unintended internals | `REL`, `CI`, `PRIV`, `CRYPTO` | Deployed artifacts are inspected and do not publish sensitive source maps, debug bundles, secret-bearing files, or unintended internal material. |

## Copy-paste launch audit prompt

```text
Use SecHelix's AI-Built App Launch Audit on this authorized application.

Start with STATIC evidence, then use LOCAL or authorized STAGING/PRODUCTION_SAFE verification only where it is safe and necessary.
Evaluate launch checks 01-36 from references/ai-built-app-launch.md.
For each relevant check return PASS, FAIL, UNKNOWN, NOT_APPLICABLE, or BLOCKED.
Do not mark PASS without exact evidence from code, configuration, policy, test, log, or a safe runtime observation.
For FAIL and security-relevant UNKNOWN results, give the realistic failure mode, the smallest root-cause fix, and an exact safe verification step.
Prioritize auth, authorization, cross-user/tenant data, private data, payments/entitlements, admin access, secrets, webhooks, AI/tool authority, and spend-sensitive routes.
Do not mutate production data or infrastructure during the audit.
After fixes, re-run the failed/unknown checks and produce the normal SecHelix release gate.
```

## Output example

| ID | Check | Result | Evidence | Failure mode / fix / verification |
|---|---|---|---|---|
| 05 | Server-side authorization | `FAIL` | `src/api/orders/[id].ts:42-58` | Route loads by ID without ownership check → enforce canonical order authorization → verify with two owned test identities. |
| 14 | Browser bundle secrets | `PASS` | production bundle inspection + env import boundary | No private credential appears in client output. |
| 31 | Webhook authenticity | `UNKNOWN` | handler found; provider verification path not evidenced | Confirm provider signature verification and replay behavior before launch. |

A launch profile can be useful even when the full SecHelix audit is larger. It is a minimum evidence filter, not a claim that these checks exhaust the attack surface.
