# SecHelix 4.0.0-alpha.2

**Date:** 2026-09-09  
**Maturity:** public alpha  
**Portable Agent Skill:** still works without the optional runtime  
**Optional Python runner:** `0.3.0`  
**Blind label evaluation:** `MEASURED`  
**Full SecHelix workflow:** `NOT_MEASURED`

A distribution release. No security semantics changed: applicability still
resolves to four states, High and Critical findings still require independent
verification, and the release gate still fails closed to `INCOMPLETE`.

What changed is how SecHelix reaches people, and how much of what it claims
about itself is now enforced by a test.

## A GitHub Action, at the repository root

```yaml
- uses: omarmohelal/SecHelix@v4.0.0-alpha.2
  with:
    executor: none
```

The action lives at the repository root, which is what makes it usable as
`uses: omarmohelal/SecHelix@<tag>` and what GitHub Marketplace requires. The
previous composite action was nested under `.github/actions/`, referenced by no
workflow, and consumable by no other repository.

`outcome` is `PASS`, `PASS_WITH_KNOWN_RISK`, `BLOCKED` or `INCOMPLETE`, derived
from the vocabulary in `sechelix_core/pr_review.py` — the same words
`scripts/security_gate.py` uses. There is no second definition of a finding.

**`INCOMPLETE` is decided before findings are examined at all.** A run whose
reasoning lanes were blocked produces an empty finding list, and so does a run
over genuinely clean code. Ordering the check this way is what stops the first
from being reported as the second — in the outputs, in the job summary, and in
the SARIF, which emits a real `sechelix/run-incomplete` result rather than an
empty `results` array that a code-scanning UI renders as "clean".

`fail-on` defaults to `blocked` rather than `incomplete`. A run that could not
analyse anything is not evidence against the pull request, and turning it into a
red X trains people to ignore red Xs. It is still reported loudly everywhere
else.

Full reference: [`docs/github-action.md`](../github-action.md).

## The MCP adapter is published to the official registry

Registered as `io.github.omarmohelal/sechelix`. Several MCP directories
re-publish from the official registry rather than crawling, so one verified
entry is worth more than several unverified listings.

Both halves of the identity are proven rather than asserted: the
`io.github.omarmohelal` namespace comes from a GitHub OIDC claim, so no registry
token is stored; PyPI ownership is proven by an `mcp-name` token in the
published package description.

The publish workflow fails closed before reaching the registry. It refuses when
`server.json`, `pyproject.toml` and the package entry disagree, and when the
PyPI release it names does not exist or does not carry the ownership token — a
registry entry pointing at a version nobody published is a dangling install
instruction, which is worse for a reader than no entry.

`tests/test_server_json.py` holds the listing to the code: tool count, stdio
transport, `sechelix mcp` remaining a real subcommand, no shell reachable from
the adapter, no credentials required, and path confinement actually refusing
`../..`, absolute paths and symlink-style escapes.

## A demo that cannot rot

[`examples/expense-api`](../../examples/expense-api/README.md) is a small
multi-tenant API with two candidates and opposite answers, reproducible in about
90 seconds on Python 3.10+ with no dependencies, no network and no containers.

The one every pattern matcher flags builds a SQL `ORDER BY` with an f-string and
is not exploitable — the sort key is mapped onto one of five module constants,
and the proof checks *by identity* that the object reaching the query text is
that constant, so the refutation is structural rather than "the payloads I tried
were rejected".

The one scanners walk past is three lines below. The endpoint *has* an
authorization check; it is correct, and an employee token really does get a
`403`. It asks "may someone like you open a receipt?" and never "is this receipt
yours?", over a query scoped by nothing.

Nothing in the walkthrough is transcribed by hand. `prove.py` asserts everything
it prints, and `tests/test_demo_expense_api.py` drives the whole thing on every
CI run in three states — vulnerable, patched in a temp copy, and reverted — so
the README cannot drift into describing a run that no longer happens.

## Two defects SecHelix found in SecHelix

The new action was reviewed with SecHelix before merging. Two findings, both
fixed in the same pull request, both of a kind that passes a functional test.

**The action uploaded the wrong copy.** `sechelix audit --json` prints the raw
result; only `storage.write_json` runs a result through the redactor. Uploading
the stdout form as a build artifact routed around the redaction boundary and
would have published secret-shaped node values to anyone with repository read
access. Reproduced against the redactor directly: the persisted projection
returns `[REDACTED]` for an `authorization` value the stdout projection returns
in full. The action now re-reads the persisted copy.

**Any output value could forge another output.** `$GITHUB_OUTPUT` is
newline-delimited, and the runner takes the last value for a repeated key, so a
forged `outcome=PASS` after a real `outcome=BLOCKED` wins the gate. `run_id` is
constrained by `RUN_ID_PATTERN` and cannot carry a newline, so this was defence
in depth rather than a reachable bypass — reported at its real severity rather
than its alarming one. Regression test confirmed red first.

A third observation was filed rather than folded in: `sechelix audit --json`
prints an unredacted result to stdout, which in a workflow without redirection
lands in the build log. Changing the shape of a published CLI's `--json` output
belongs in its own change. See issue #76.

## Version agreement is now a test

The 0.3.0 PyPI publish failed closed because `pyproject.toml` said `0.3.0` while
`RUNNER_VERSION` still said `0.2.1`. The gate was right. Four places declare
this version, they now agree, and a test fails when they drift.
